Manual del SCADA Node3

Bienvenido al manual técnico de tu SCADA. Este documento explica cómo interactúan las distintas partes del sistema (Node.js, HTML/JS en el navegador y el PLC vía Modbus).

1. Instalación y Auto-arranque

Para poner en marcha el SCADA en un ordenador nuevo, sigue estos pasos estrictamente:

A. Requisitos previos

  • Node.js: Descarga e instala la versión v18 LTS o superior (recomendado v18.20.8) desde nodejs.org.
  • Acceso de Red: El PC debe tener una IP fija en el mismo rango que los PLCs (ej: 192.168.0.XXX).

B. Instalación del Software y PLC

✅ OPCIÓN 1: Instalación Rápida (Recomendada para Usuarios)
  1. Copia la carpeta stable/ (última versión estable) al disco local.
  2. Abre una terminal (PowerShell o CMD) en esa carpeta.
  3. Ejecuta: npm install (instala todas las dependencias).
  4. Ejecuta: node server.js para arrancar.
🔌 Carpeta PLC (Para Simulación o Conexión Real)

Dentro de la carpeta PLC/ encontrarás:

  • ModbusTCP_S7-1500.zap18: Proyecto completo de TIA Portal (Siemens S7-1500) listo para importar.
  • FC_Sim_Produccion.scl: Código fuente del bloque de función para simulación/producción.

Importa el proyecto .zap18 en TIA Portal para simular la máquina o conectar con un PLC real. El SCADA se comunica a través de Modbus TCP en el puerto 505 (configurable en config/plcs.json).

⚠️ NOTA TÉCNICA IMPORTANTE:
  • Librería Modbus: Este SCADA utiliza jsmodbus específicamente para comunicación TCP/IP optimizada.
  • Puerto de Red: El servidor escucha en el Puerto 4000. Asegúrese de que el Firewall de Windows permita este puerto.
  • Package.json: Las dependencias críticas son express, socket.io y jsmodbus.
✅ OPCIÓN 2: Instalación Completa (Para Desarrolladores)
  1. Copia toda la carpeta ScadaNode3 al disco local (recomendado C:\ScadaNode3).
  2. Abre una terminal (PowerShell o CMD) en esa carpeta.
  3. Ejecuta el comando: npm install. Esto descargará todas las librerías necesarias.

C. Configuración de Auto-arranque (Windows)

Para que el SCADA arranque solo al encender el PC y se reinicie si hay un error, usamos PM2:

  1. Instala PM2 globalmente: npm install pm2 -g
  2. Inicia el servidor: pm2 start server.js --name "SCADA-NODE3"
  3. Guarda la configuración: pm2 save
  4. Para que arranque con Windows, instala el servicio de inicio: npm install pm2-windows-startup -g y luego ejecuta pm2-startup install.
Tip: Puedes ver el estado del servidor en tiempo real con el comando pm2 monit.

Flujo de Datos

  1. PLC: Almacena los datos en registros Modbus.
  2. server.js: Lee al PLC cada 500ms y "emite" los datos por WebSockets.
  3. Navegador: Recibe los datos y los dibuja en pantalla (luces, textos, gráficas).
  4. Acción del Usuario: Al pulsar un botón, el navegador envía una orden al servidor, y este escribe en el PLC.

3. Introducción al Sistema

El SCADA se divide en dos grandes piezas:

  • El Backend (Servidor): Es el archivo server.js. Funciona continuamente en segundo plano utilizando Node.js. Es el único que "habla" directamente con el PLC (a través de TCP/IP usando el protocolo Modbus).
  • El Frontend (Navegador): Son los archivos HTML, CSS y JS de la carpeta public. Muestran la interfaz gráfica y solo se comunican con el Backend a través de "WebSockets" (Socket.io), nunca hablan directo con el PLC.

4. Comunicación (Modbus & Sockets)

El servidor Node.js tiene un ciclo continuo llamado "Polling". Cada 500 milisegundos, le hace una pregunta al PLC: "Oye, dame el valor de tus palabras desde la W0 hasta la W59".

Cuando el servidor recibe esos datos del PLC, los empaqueta y los "grita" a todas las páginas web conectadas usando WebSockets. Esto se hace mediante el evento plc_update.

// server.js: Envío periódico a la web
io.emit('plc_update', {
  id: 'PLC1',
  status: true,
  regs: memoria,     // Arreglo crudo [12, 0, 512, ...]
  tags: tagsValues   // Diccionario amigable { FBK_POMPA_ACCESA: 1, ... }
});

En tu navegador, cada página tiene una función que "escucha" este grito y actualiza las luces y textos de la pantalla:

// public/js/main.js: El navegador recibe los datos
socket.on('plc_update', (data) => {
  m1_update(data); // Actualiza la pestaña de la máquina 1
});

5. Lectura de Datos (Tags vs Words)

Las palabras (Words) Modbus son números de 16 bits (desde 0 hasta 65535). Trabajar directamente con el registro W14 es confuso. Por eso usamos un diccionario (Tags) en config/tags_plc1.js.

El servidor usa una función mágica llamada buildTagValues. Esta función lee tu lista de Tags y, si un Tag especifica un "bit", extrae solo ese bit. Si no, extrae la palabra entera.

// Ejemplo de Tag de un Bit (Luz)
{ name: 'FBK_START_CICLO', word: 1, bit: 9 }

// Ejemplo de Tag de una Palabra (Temperatura)
{ name: 'TEMP_SP_SUP', word: 14, bit: null }

Por eso en tu código m1.js (en el navegador) puedes encender un LED usando nombres fáciles en vez de lidiar con máscaras de bits:

if (tags.FBK_START_CICLO) ledCiclo.classList.add('on');

6. Escritura y Comandos (Sistema Read-Modify-Write)

Cuando pulsas un botón, el navegador envía una orden al servidor. Para mayor seguridad, el sistema utiliza ahora un mecanismo de escritura de bits individuales.

Mejora de Seguridad: El servidor ya no sobrescribe la palabra entera a ciegas. Ahora recibe el evento escribir_bit, lee el valor actual de la palabra en su memoria, cambia solo el bit solicitado y envía el resultado al PLC. Esto evita interferencias si otros bits de la misma palabra (ej. W60 o W61) cambian al mismo tiempo.

7. Botones y Pulsadores (Flancos y Flujo de Datos)

        
En los PLC, botones como el "Start" o el "Reset" suelen reaccionar al flanco de subida (el instante en que la señal pasa de 0 a 1).

        
Si el SCADA manda un 1 y nunca lo devuelve a 0, el PLC recibe el primer 1, ejecuta la acción, pero si lo presionas otra vez, el PLC sigue viendo un 1; ¡no hay nuevo flanco!

        
        
A. Lógica de Pulsación Momentánea

        
Para solucionar esto, simulamos un Pulsador Momentáneo que presiona y suelta el botón tras un tiempo de seguridad:

        
function m1_cmdStartCiclo() {
  // 1. El dedo presiona: Envía un '1'
  m1_setBit(CMD_ADDR_CICLO, 9, 1);  
  
  // 2. El dedo suelta: Espera y envía un '0'
  setTimeout(() => m1_setBit(CMD_ADDR_CICLO, 9, 0), 200);
}


        
B. Flujo de Datos Paso a Paso

        
Es vital entender el camino que recorre tu clic hasta llegar a la máquina:

        
    
          
  1. Navegador (Frontend): Detecta el click y envía un evento escribir_bit vía Socket.io.
    2. 
          
  2. Servidor (Backend): Recibe el evento, identifica el PLC por su ID (ej. "PLC1") y traduce la orden al protocolo Modbus TCP.
    3. 
          
  3. Red Industrial: El servidor envía el paquete TCP/IP a la dirección IP del PLC.
    4. 
          
  4. PLC (Hardware): Recibe la orden y activa la salida o marca correspondiente. La acción física ya ha ocurrido.
    5. 
          
  5. Confirmación Visual: Para que veas el LED encendido en la web, el servidor debe realizar el siguiente ciclo de Polling (lectura), recibir el estado actualizado y enviarlo de vuelta al navegador.
    6. 
        


        

          🚀 Optimización de Respuesta:
          
Si notas el sistema "perezoso", puedes ajustar dos valores:

          
    
            
  • Polling (config/plcs.json): Bajando de 500ms a 200ms, los LEDs reaccionarán mucho más rápido a tus acciones.
    • 
            
  • Timeouts (JS): En comandos secuenciales (como el Start Total), un tiempo de 100ms es suficiente para que el PLC Siemens procese cada orden antes de recibir la siguiente.
    • 
          

        

      


      
      

        
Lógica de Detección

        
El servidor compara en cada ciclo de lectura (500ms) el estado actual de los tags de categoría "Alarma" con el estado anterior guardado en memoria. Si detecta un cambio, escribe una línea en data/alarms.jsonl.

        
        
Descripciones Dinámicas

        
A diferencia de versiones anteriores, el sistema ahora es totalmente dinámico. Los textos de las alarmas no están fijos en el código del navegador, sino que se leen directamente del diccionario de tags (TAGS_DICT). Esto permite que, si añades una alarma nueva en el PLC y la defines en el diccionario, aparecerá automáticamente en la web con su descripción correcta.

El SCADA incluye un sistema de notificaciones por email para alertar sobre eventos críticos de producción. Este sistema utiliza la librería nodemailer y puede configurarse para diferentes proveedores (Gmail, Ethereal, etc.).


        
Configuración

        
El archivo de configuración se encuentra en config/email.json:

        
{
  "enabled": true,
  "host": "smtp.ethereal.email",
  "port": 587,
  "auth": {
    "user": "usuario@ethereal.email",
    "pass": "contraseña"
  },
  "notifications": {
    "to": "destinatario@ejemplo.com",
    "subject": "⚠️ ALERTA SCADA",
    "onAlarm": true,
    "onRecovery": true,
    "maxInactivityMin": 1
  }
}


        

          Parámetros de Configuración:
          
    
            
  • enabled: Activa/desactiva el sistema de emails.
    • 
            
  • host/port: Servidor SMTP y puerto (ej: smtp.gmail.com:587).
    • 
            
  • auth: Credenciales de autenticación.
    • 
            
  • onAlarm: Envía email al activarse una alarma.
    • 
            
  • onRecovery: Envía email al recuperarse de inactividad.
    • 
            
  • maxInactivityMin: Minutos de parada en AUTO antes de alertar.
    • 
          

        


        
Tipos de Notificaciones

        
El sistema gestiona dos tipos de eventos:

        
    
          
  1. Alarmas: Email instantáneo cuando se activa una alarma. No envía notificación al normalizarse (minimalismo).
    2. 
          
  2. Inactividad en Producción: Si la máquina está en modo AUTO pero sin producción durante el tiempo configurado, envía alerta. Al volver a producir, envía notificación de recuperación.

Para evitar múltiples emails cuando varias alarmas se activan simultáneamente, el sistema implementa un cooldown de 60 segundos por PLC. Solo se envía un email por PLC cada minuto, independientemente de cuántas alarmas se activen.

9. Sistema de Recetas (El flujo JSON -> PLC)

        
Para entender las recetas, es vital distinguir entre el Frontend (lo que ves en el navegador) y el Backend (el servidor Node.js que corre en el PC).

        
        

          Conceptos Clave:
          
    
            
  • Frontend (Browser): Gestiona la visualización. No tiene permiso para escribir archivos en el PC por seguridad.
    • 
            
  • Backend (Server.js): Centraliza todo. Lee/Escribe el archivo recipes.json y es el único que envía datos al PLC vía Modbus.
    • 
          

        


        
El "Truco" del intercambio de Receta

        
Cuando seleccionas una receta y pulsas "Enviar al PLC", se desencadena este proceso de 5 pasos:

        
    
          
  1. Web -> Servidor: El navegador envía todos los valores (tiempos, temperaturas y el ID de receta) al servidor Node.js.
    2. 
          
  2. Servidor -> PLC (W62-W76): El servidor escribe los parámetros de proceso en las palabras correspondientes del PLC.
    3. 
          
  3. Servidor -> PLC (W77): El servidor escribe el Número de Receta en la palabra de consigna W77 (SET_NUM_RECETA).
    4. 
          
  4. Lógica del PLC (TIA Portal): Tu programa en el PLC debe detectar el valor en W77 y realizar un MOVE hacia la palabra W28 (NUM_RECETA_ACTUAL). Esto sirve como acuse de recibo.
    5. 
          
  5. PLC -> Web (Confirmación): El SCADA lee la W28 constantemente. En cuanto el valor cambia, la web muestra el nombre de la receta confirmando que el PLC ya la está ejecutando.
    6. 
        


        
// Flujo simplificado:
[Navegador] --(petición)--> [Server.js] --(Modbus)--> [W77 PLC] --(MOVE)--> [W28 PLC] --(Lectura)--> [Navegador OK]

        

          ⚠️ IMPORTANTE - SINCRONIZACIÓN DE TAGS:

          Este SCADA usa dos diccionarios que deben estar siempre iguales:
          
    
            
  • config/tags_plc1.js (Cerebro del Servidor)
    • 
            
  • public/js/tags_dict.js (Cerebro del Navegador)
    • 
          

          Si añades o cambias un nombre de variable, hazlo en ambos archivos para evitar que la web muestre datos vacíos o nombres incorrectos.
        

      

        
El servidor Node recibe esta avalancha de peticiones y, para no saturar al PLC Siemens, usa
          writeSingleRegister. A los 500ms (en el siguiente Polling
          de lectura), el SCADA refrescará la pantalla mostrando los nuevos valores leídos del PLC.

10. Múltiples PLCs y Configuración

El SCADA está diseñado con arquitectura modular para escalar a decenas de PLCs. Node.js maneja múltiples conexiones Modbus de forma asíncrona (es decir, atiende a PLC1 y PLC2 de forma simultánea sin que uno ralentice al otro).

1. Configuración del Archivo plcs.json

Añadir una segunda máquina es tan sencillo como duplicar el bloque JSON en config/plcs.json y cambiar su id y su host (IP):

{
  "devices": [
    {
      "id": "PLC1",
      "host": "192.168.0.1",
      "port": 505,
      ...
    },
    {
      "id": "PLC2",
      "host": "192.168.0.2",
      ...
    }
  ]
}

2. Instanciación en server.js

El servidor tiene una función fábrica llamada createPlcController. Crea un controlador aislado para PLC2 pasándole sus tags propios:

const plc2Device = devices.find(d => d.id === 'PLC2');
plcControllers.PLC2 = createPlcController(plc2Device, tagsPlc2);

3. El Navegador (Frontend)

El evento WebSocket plc_update enviará ahora paquetes tanto de PLC1 como de PLC2. El identificador mágico es data.id. En tu JavaScript, debes redirigir la información a la pestaña de máquina correcta:

socket.on('plc_update', (data) => {
  if (data.id === 'PLC1') m1_update(data);
  else if (data.id === 'PLC2') m2_update(data);
});

Igualmente, para enviar un botón a la Máquina 2, solo cambias el ID en la emisión:
socket.emit('escribir', { id: 'PLC2', addr: 60, value: 512 })

11. Analítica y Producción (Data Logging)

El sistema ha evolucionado de un simple panel de control a una herramienta de gestión de eficiencia. Esta sección explica cómo se capturan y representan los datos de producción.

Registro de Datos (Backend)

El servidor server.js ejecuta una tarea programada que realiza una "fotografía" de los tags clave del PLC. Esta captura se guarda en el archivo data/production.jsonl utilizando el formato JSON Lines.

A diferencia de las alarmas (que se graban por evento), la producción se graba por intervalo de tiempo. El intervalo por defecto es de 30 minutos, pero puede ser ajustado dinámicamente desde el dashboard.

// server.js: Captura de snapshot de producción
function logAllPlcsProduction() {
  const snapshot = {
    timestamp: new Date().toISOString(),
    plc: 'PLC1',
    PROD_ACTUAL_GOLPES: tags.PROD_ACTUAL_GOLPES,
    CONSUMO_ENERG_ACTUAL: tags.CONSUMO_ENERG_ACTUAL,
    ...
  };
  fs.appendFileSync('data/production.jsonl', JSON.stringify(snapshot) + '\n');
}

Visualización (Dashboard Independiente)

La página analytics.html es un módulo independiente que utiliza Chart.js para convertir los datos históricos en gráficos comprensibles. Al ser una página autónoma (standalone), cuenta con su propio archivo de estilos css/analytics.css y lógica js/analytics.js, lo que permite abrirla en múltiples monitores sin interferir con el panel de control principal.

Configuración del Intervalo

Desde el Dashboard, el usuario puede modificar la frecuencia de muestreo. Al pulsar "Aplicar", se envía una petición POST a la API /api/production/interval, que reinicia el temporizador del servidor sin necesidad de reiniciar el SCADA.

Exportación PDF: Se utiliza la librería jsPDF para generar reportes técnicos en el lado del cliente. El informe incluye un resumen de los KPIs (indicadores clave de rendimiento) y una tabla con los últimos 100 registros cronológicos para su impresión o archivo.
📊 Exportación CSV para Power BI / Excel:

Además del registro interno, el SCADA genera automáticamente archivos .csv con rotación mensual en la carpeta data/.

  • Formato: CSV compatible con Excel en español (delimitado por punto y coma ;).
  • Frecuencia: Sincronizada con el intervalo de analítica (por defecto cada 10 min).
  • Uso en Power BI: Seleccione "Obtener datos -> Texto/CSV" y apunte al archivo mensual. No requiere transformación de datos previa ya que el SCADA incluye la fila de encabezados automáticamente.

12. Gestión de Tiempos

Es fundamental distinguir entre los tres niveles de temporización del sistema:

1. Ciclo PLC

Definido en el bloque FB_Sim_Produccion (TIA Portal). Determina la velocidad a la que se incrementan los contadores y cambian las temperaturas reales en la máquina.

2. Registro Servidor

Es el Reloj Maestro. Se configura desde la página de Analítica (Aplicar). Decide cada cuánto tiempo se guarda un punto en la base de datos (Snapshots).

3. Refresco Web

Es puramente visual. La página de Analítica se recarga automáticamente cada 5 minutos para mostrar los nuevos datos que el servidor haya capturado.

13. Lógica Interna del Servidor (Server.js)

El servidor Node.js no solo actúa como puente Modbus, sino que gestiona tres motores críticos de datos:

13.1 Motor de Recetas (API CRUD)

Gestiona el archivo data/recipes.json mediante cuatro endpoints estándar:

  • GET /api/recipes: Carga la lista completa de recetas.
  • POST /api/recipes: Crea una nueva receta asignando un ID único (Timestamp).
  • PUT /api/recipes/:id: Sobrescribe una receta existente.
  • DELETE /api/recipes/:id: Elimina una receta del archivo.

13.2 Detección de Alarmas (Diferencial)

El servidor compara en cada ciclo de lectura (500ms) el estado actual de los tags de categoría "Alarma" con el estado anterior guardado en memoria:

// Fragmento de lógica en server.js
function logAlarms(id, currentTags) {
    const alarmTags = tagsPlc1.filter(t => t.cat === 'Alarma' || t.name.startsWith('ALM_'));
    alarmTags.forEach(tag => {
        if (currentTags[tag.name] !== lastAlarmsState[id][tag.name]) {
            const entry = {
                date: new Date().toISOString(),
                fecha_es: new Date().toLocaleString('es-ES'),
                plc: id,
                tag: tag.name,
                status: currentTags[tag.name] ? 'ACTIVADA' : 'NORMALIZADA'
            };
            fs.appendFileSync('./data/alarms.jsonl', JSON.stringify(entry) + '\n');
        }
    });
}

13.3 Motor de Analítica (Snapshots)

La función logProduction() realiza capturas de estado de forma cíclica:

// Generación de snapshot en server.js

14. Arquitectura de Intercambio (DB1 Modbus)

Para la comunicación entre el PLC y el SCADA, se ha implementado un bloque de datos global (DB1) que actúa como zona de intercambio común. Esta elección técnica busca la máxima eficiencia en la lectura masiva de datos.

Configuración del DB1:
  • Tipo de dato: Array [0..119] of Word.
  • Nombre en PLC: "Modbus_Data".Data_Array
  • Acceso: Direccionamiento directo por índice (0-119).

Lógica de direccionamiento

Cada índice del array corresponde exactamente a una palabra (Word) de Modbus en el servidor:

// Ejemplo de uso en SCL (PLC)
"Modbus_Data".Data_Array[43] := #MiEstado; // Escribe en W43
#MiConsigna := "Modbus_Data".Data_Array[84]; // Lee de W84

Ventajas de este método:

  • Velocidad: El SCADA lee las 120 palabras en un solo paquete Modbus (0.1ms).
  • Simplicidad: No requiere conversiones de tipos de datos complejas en el servidor.
  • Mantenimiento: El archivo config/tags_plc1.js del SCADA es el espejo exacto de este array.

Nota: Se recomienda llevar un control estricto de los índices utilizados para evitar colisiones de datos.

16. Guía de Operación Rápida

Esta sección resume los procedimientos habituales para el operador de planta.

Gestión de Recetas

  • Editar: Al pulsar el icono de lápiz, los valores de la receta se cargan en el formulario de la derecha.
  • Guardar: Almacena los cambios en el disco duro del SCADA (archivo recipes.json).
  • Enviar al PLC: Envía los parámetros actuales directamente a la memoria del PLC (registros W62–W76). La máquina adoptará estos valores inmediatamente.

  • Franja Roja: Aparece automáticamente cuando hay una anomalía activa. Muestra el texto descriptivo definido en el diccionario.
  • Reset de Anomalías: En la página de alarmas, el botón de "Reset" envía un pulso al bit 1 de la palabra W61 del PLC para intentar rearmar el sistema.
  • Historial: Todas las alarmas se graban con fecha y hora exacta para auditorías posteriores.

Mantenimiento del Sistema

  • Arranque manual: Si el sistema no arranca solo, abre una terminal en C:\ScadaNode3 y ejecuta node server.js.
  • Acceso remoto: Se puede acceder desde cualquier PC de la red introduciendo la IP del servidor y el puerto 4000 (ej: http://192.168.0.100:4000).

17. Sistema de Autenticación

El SCADA implementa un sistema de autenticación basado en sesiones para proteger el acceso a la interfaz de control. Este sistema garantiza que solo usuarios autorizados puedan operar la máquina y enviar comandos al PLC.

17.1 Configuración de Usuarios

Los usuarios se definen en el archivo config/users.json. Cada usuario tiene tres propiedades:

{
  "users": [
    {
      "username": "admin",
      "password": "admin123",
      "role": "admin"
    },
    {
      "username": "operador",
      "password": "oper123",
      "role": "operador"
    }
  ]
}
⚠️ Seguridad:
  • Las contraseñas se almacenan en texto plano. Para producción, considera implementar hashing (bcrypt).
  • El archivo users.json debe protegerse con permisos de archivo restrictivos en el servidor.

17.2 Flujo de Autenticación

El proceso de login sigue estos pasos:

  1. Pantalla de Login: El usuario accede a /login.html e introduce sus credenciales.
  2. Envío al Servidor: El formulario envía una petición POST /api/login con usuario y contraseña.
  3. Verificación: El servidor busca el usuario en config/users.json y valida las credenciales.
  4. Creación de Sesión: Si las credenciales son correctas, se crea una sesión con express-session y se almacena el usuario en req.session.user.
  5. Redirección: El navegador redirige a /index.html (panel principal).
// server.js: Endpoint de login
app.post('/api/login', (req, res) => {
  const { username, password } = req.body;
  const user = usersConfig.users.find(u => u.username === username && u.password === password);
  
  if (user) {
    req.session.user = { username: user.username, role: user.role };
    res.json({ success: true, user: { username: user.username, role: user.role } });
  } else {
    res.status(401).json({ success: false, error: 'Credenciales inválidas' });
  }
});

17.3 Middleware de Protección

El servidor incluye un middleware requireAuth que protege las rutas sensibles. Este middleware verifica que exista una sesión activa antes de permitir el acceso:

// server.js: Middleware de autenticación
const requireAuth = (req, res, next) => {
  if (req.session.user) {
    next();
  } else {
    res.status(401).json({ error: 'No autenticado' });
  }
};

17.4 Verificación de Sesión en el Frontend

Al cargar la página de login, el frontend verifica automáticamente si el usuario ya está autenticado mediante el endpoint GET /api/me:

// public/js/login.js: Verificación de autenticación
async function checkAuth() {
  try {
    const response = await fetch('/api/me');
    const data = await response.json();
    
    if (data.authenticated) {
      window.location.href = '/index.html';
    }
  } catch (error) {
    console.error('Error verificando autenticación:', error);
  }
}

17.5 Cierre de Sesión (Logout)

El usuario puede cerrar sesión mediante el endpoint POST /api/logout, que destruye la sesión en el servidor:

// server.js: Endpoint de logout
app.post('/api/logout', (req, res) => {
  req.session.destroy();
  res.json({ success: true });
});

17.6 Roles de Usuario

El sistema soporta roles diferenciados (admin, operador) que pueden utilizarse para implementar permisos granulares en el futuro. Actualmente, el rol se almacena en la sesión pero no se aplica lógica de restricción específica.
